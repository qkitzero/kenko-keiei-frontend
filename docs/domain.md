# ドメインガイド

画面が扱う概念と、上流サービスの癖をまとめる。見た目とコンポーネントの規則は `docs/design.md`。

## テナントと組織

**テナント**と**組織**は別の概念で、UI でも語を混ぜない。

- **テナント**: user-service の group。利用者が所属する単位で、`/tenants` で管理する。識別子は `tenantId`（BFF の `/api/group/*` は上流の API 名に合わせて `group` のまま）
- **組織**: fitness-service の Organization。テナント配下にあり顧客の所属先になる。`/organizations` で管理する。識別子は `organizationId`

テナントの実体は user-service にあるが、**テナントの住所・連絡先（テナントプロフィール）は fitness-service が持つ**。BFF も `/api/fitness/tenant/{tenantId}/profile` で user-service 由来の `/api/group/*` とは別系統になる。未登録のテナントでは上流が 404 を返すので、エラーではなく空のフォームとして表示する。非メンバーも同じ 404 なので、カード自体は `memberships` で出し分ける。参照実装: `src/components/TenantProfileCard.tsx`

## テナントスコープ

「いまどのテナントを見ているか」は**トップバーの `TenantSwitcher` が唯一の情報源**。`TenantsContext` の `selectedTenantId` / `selectTenant` を使う。

- **ページ内にテナントセレクタを置かない**。同じ意味の選択肢が複数箇所にあると、どれが効いているのか分からなくなる。テナントで絞り込む画面は `selectedTenantId` を読むだけにし、対象のテナント名は見出しの説明文に**確認表示**として出す
- 選択値は `localStorage` に保存し、`memberships` に無い値は自動で先頭のテナントにフォールバックする（権限を失ったテナントに固定されないようにする）
- テナントスコープを持つ一覧は URL の `?tenantId=` に反映する（共有・ブックマーク・戻る操作のため）。URL の値が非メンバーなら選択中のテナントで URL を書き直す
- `/tenants/{tenantId}` のように特定のテナントのページを開いたときは、そのテナントを選択状態に同期する。逆にそのページでテナントを切り替えたら、そのテナントの同じページへ移動する
- **同期するのは所属しているテナントのときだけ**。下位テナントのように自分が所属していないテナントのページでは選択状態を変えず、トップバーもテナント名を出さない（別テナントを選択中だと主張しない）
- 選択状態を書き換える API は `selectTenant` だけにし、選択が変わった回数（`scopeVersion`）でリンク由来のスコープと利用者の選択を区別する。「リンクの `tenantId` を採用済みか」を ref で覚えると、テナント取得の失敗や effect の実行順で取りこぼす

一覧を絞り込む**フィルタ**（「無効な顧客も表示する」など）はスコープとは別物なので、ページ内に置いてよい。ただし状態は URL のクエリに反映し、共有・再読込・戻る操作で保たれるようにする。参照実装: `src/app/customers/page.tsx` の `includeInactive`

参照実装: `src/context/TenantsContext.tsx`, `src/components/TenantSwitcher.tsx`, `src/lib/navigation.ts`

## 測定

**測定項目マスタ**は fitness-service の MeasurementItem で、**テナントを持たないシステム共通のデータ**。顧客配下ではないので `/measurement-items` に独立して置き、サイドバーに出す。テナントで絞り込まない（`useTenantScope` を使わない）。上流は `code` / `name` / `category` / `unit` / `trialCount` / `bilateral` / `valueType` しか返さないので、**判定の対象かどうか（`score_direction`）と要素（筋力・バランスなど）の対応は画面から分からない**。項目の解説文はフロントが `code` をキーに持つ（`src/lib/measurementGuide.ts`）。

**測定**は fitness-service の Measurement で、顧客に属する。テナントや組織のような独立した管理対象ではないので、**サイドバーには出さず顧客詳細を起点にする**。

- 顧客詳細の「測定履歴」セクションが一覧で、そこから記録ページ（`/customers/{customerId}/measurements/new`）と詳細ページ（`/customers/{customerId}/measurements/{measurementId}`）に入る。参照実装: `src/components/MeasurementHistory.tsx`
- 専用の測定一覧ページは作らない。上流の `ListMeasurements` が1リクエストで全件返すので、顧客詳細のセクションに新しい順で並べる
- 上流の取得・更新・削除は `measurementId` だけで引けるが、**URL は顧客配下にネストする**。パンくずと戻り先が自然になるため。`measurement.customerId` が URL の `customerId` と一致しない場合は「測定が見つかりません」にする（URL の付け替えで別顧客の測定を表示しない）
- **測定項目マスタ（MeasurementItem）はテナント非依存のグローバルマスタ**で、フロントから追加・編集はできない。取得は `src/lib/useMeasurementItems.ts`
- **並び順はサーバーの順序に従う**（カテゴリ順 → コード順）。フロントで並べ替えない。逆に**測定のレスポンスの `entries` は測定項目 ID 順で意味のある順序ではない**ので、表示・入力は必ず項目マスタの順序で組む
- **下書きと確定は `isDraft` で区別し、UI では入力項目ではなくボタンの選択として表す**。フォームに下書きのチェックボックスを置くと「保存」と「どう保存するか」が2箇所に分かれる。下書きの測定は「下書きとして保存」「確定して保存」の2ボタン、確定済みは「変更を保存」1つ（確定を巻き戻す操作は用意しない）
- **保存操作が2つあるフォームでは Enter による暗黙送信で保存しない。** どちらのボタンも `type="button"` にし、`form` の `onSubmit` は `preventDefault` だけにする（送信ボタンが1つのフォームは通常どおり `type="submit"` を明示する）。確定は巻き戻せないので、下書きから確定するときは `window.confirm` で確認する
- 取得系は **401 を「サインインの有効期限が切れました」+ `LoginButton` に分岐する**。汎用エラーに潰すと、再試行しても成功しない行き止まりになる。共通のフェッチは `src/lib/useResource.ts`（`loading` / `ok` / `unauthenticated` / `error` の4状態）に置き、`useMeasurementItems` / `useMeasurements` はその薄いラッパーにする
- **マスタの変更で表示できなくなった値は警告する。** 項目 ID が消えた場合だけでなく、試行回数・左右の設定が変わって入らなくなった値も `measurementDataLoss` で数え、保存すると失われることを伝える
- 測定時の年齢はサーバーが顧客の生年月日から計算するので、読み取り専用の表示にする
- **測定者（`measuredBy`）は BFF が埋め、クライアントからは受け取らない**。作成時は `/v1/verify` の `userId`、**更新時は上流から取り直した既存の `measuredBy` をそのまま送り返す**。`/api/user/get` の `userId` は user-service が発行した別の識別子で、上流が `updatedBy` に入れる値と体系が違う。上流の `UpdateMeasurement` は渡された値で `measured_by` を上書きするので、編集者で埋めると「実際に測定した人」が消える。表示はしない（識別子しか無く名前に解決できないため）

### 項目 × 試行 × 左右の入力

「1項目に複数の値がある」入力は、項目ごとに1ブロックを作り、その中で試行と左右を展開する。参照実装: `src/components/MeasurementFields.tsx`

- **行 = 左右、列 = 試行**の表にする。試行が1回だけなら列見出しを出さず、左右が無ければ行見出しも出さず、入力欄1つだけにする
- 表の入力欄は `label` を持てないので `aria-label` に「項目名（2回目・左）」のような位置つきの名前を渡す。列・行見出しだけでは支援技術に伝わらない
- 横に収まらない場合はグリッドを `overflow-x-auto` でラップする。ページの幅は変えない
- 「測定不可」のような値を無効化するチェックボックスは、**オンにしたときに入力値を消す**。値を残したまま送るとサーバーが弾くので、UI 側で状態を一貫させる

### 派生値

**BMI と適正体重はマスタの測定項目ではなく、身長・体重から算出する**。上流はこれらを項目として持たず、算出は呼び出し側の責務になっている。

- 項目の特定は**名称や ID ではなく `code`（`height` / `weight`）で行う**。名称は変わりうるし、項目 ID は環境ごとに違う
- 単位が期待どおり（`UNIT_CM` / `UNIT_KG`）でなく、値の型が `VALUE_TYPE_NUMERIC` でもなければ算出しない。マスタが変わったときに桁のずれた値や、対の片方だけを使った値を出さない
- **どの値を使うかを順序に依存させない**。試行・左右が増えても結果が揺れないよう、`(試行番号, 左右)` で並べ替えてから先頭を採る。レスポンスの配列順に意味は無い
- 適正体重は BMI 22 を基準に `身長(m)² × 22`、BMI の区分は日本肥満学会の基準（18.5未満 低体重 / 25未満 普通体重 / 以降 肥満1〜4度）
- **区分は表示する丸めた値から求める**。丸める前の値で区分を決めると、境界で「25.0（普通体重）」のように数字とラベルが食い違う
- **算出値であることを画面に明記する**。測定した値と同じ見た目で並べると、実測値だと誤解される。カテゴリの中に混ぜず「算出値」として独立させる（上流がマスタの分類を変えても表示が消えない）。実装は `src/lib/measurement.ts` の `bodyComposition`

## 判定

**判定**は fitness-service の Judgment で、測定に従属する。測定ごとに1つで、値は保存されておらず**取得のたびにサーバーが基準値から計算する**（保存されているのはアドバイスだけ）。

- 測定と同じく顧客配下にネストし、`/customers/{customerId}/measurements/{measurementId}/judgment` に置く。測定詳細は編集フォームで既に長いので、判定は**別ページに分ける**。タブは作らず、測定結果 → 項目別 → 要素別 → 運動器年齢 → アドバイスの順にセクションを縦に並べる。**生の値から集約へ、サーバーが計算する順に並べる**（項目の z スコア → 要素の z スコア → 運動器年齢）。結論を先頭に置くと、測定値を先に出す構成と噛み合わず、詳細 → 要約 → 詳細のジグザグになる。運動器年齢をアドバイスの直前に置くと「結論 → 助言」で繋がる
- **下書きの測定でも判定は返る**。`isDraft` は測定の下書き状態そのままなので、確定前は暫定である旨を画面に出す
- 取得系は測定と同じく **401 を「サインインの有効期限が切れました」に分岐する**。取得は `src/lib/useJudgment.ts`

### 評価できる範囲が測定項目より狭い

**判定の対象は運動機能の項目だけ**で、バイタル・形態・体組成には基準値が無い。さらに基準値は**20〜79歳・男女ぶんしか登録されていない**（5歳刻み × 2性別）。

- **範囲外は 200 と空配列で返る。エラーではない。** 空状態の設計が機能の一部になる
- 空になる原因は「性別が男女以外」「年齢が基準値の範囲外」「運動機能の項目を測っていない」の3つで、**API のレスポンスからは区別できない**。ただしフロントは顧客と測定を持っているので理由を推定して説明できる。判定は `src/lib/judgment.ts` の `emptyJudgmentMessage`
- **推定の材料が欠けているときは理由を断定しない**。顧客を取得できていなければ性別を確認できないので、「理由を特定できません」と伝える。取れなかった事実を伏せて別の理由を示すと、利用者は測定をやり直しに行く
- 性別が未登録（`GENDER_UNSPECIFIED`）のときはラベルが空文字になるので、**空の鉤括弧を含む文にしない**。登録を促す文言に分ける
- 「運動機能を測っていない」の判定では**選択肢型（立ち上がりなど）も測定済みとして数える**。数値の値だけを見ると、記録済みの項目を「測っていない」と言ってしまう
- `JUDGMENT_MIN_AGE` / `JUDGMENT_MAX_AGE` は上流の seed を写したもので、**空状態の理由を説明するためだけに使う**。判定できるかどうかの判断には使わない（それを決めるのはサーバー）
- **運動器年齢（`motorAge`）は算出できないことがある**。全年代の基準値がそろっている項目が要るため、項目別評価が出ていても運動器年齢だけ空になりうる

### 測定値の表示

判定ページには**判定された項目だけでなく、記録された全項目を読み取り専用で載せる**。判定の対象は運動機能だけなので、これが無いとバイタル・形態・体組成が画面から消える。

- 判定の表（代表値）と測定結果（入力した値そのもの）は**別のセクションに分ける**。同じ項目が2箇所に出るが、答えている問いが違う（「どう評価されたか」と「何を測ったか」）ので、片方に寄せない
- **測定結果は判定より先に置く**。後ろに置くと、判定を読んだあとに同じ項目名が違う数字で再登場するので重複に見える。「測った値 → その評価」の順なら 2 つの数字の関係が読める
- **運動機能を測定結果から外さない。** 判定の表に無いものがここにしか無い。基準値を持たない項目（立ち上がり）、試行別・左右別の入力値、測定不可のフラグ、備考がそれにあたる。画面なら測定詳細に戻れるが、**紙には他にどこにも出ない**
- **運動機能だけ別のカードに出す**（「運動機能の記録」）。カテゴリごとの件数が偏っており（運動機能12件に対し他は各2件）、1枚のカードに全部入れると20行の一続きのリストになって読み取れない。逆にカテゴリごとに5枚へ割ると、2行しかないカードが4枚できて枠が勝つ
- 並びはカテゴリ順・マスタ順。表示は `src/components/MeasurementValues.tsx`、整形は `src/lib/measurement.ts` の `measurementDisplayEntries`
- **判定が空でも、判定の取得に失敗しても、測定結果は出す**。判定できないことと、測定の記録が無いことは別。ただし判定を読み込めていないときはアドバイスの編集欄を出さない（既存のアドバイスが見えないまま空で保存すると消える）
- **判定が空でも印刷はできる**。判定が空になるのは 19 歳以下・80 歳以上・性別が男女以外といった**永続的で正当な状態**なので、そこで印刷を塞ぐとその顧客には一生紙を渡せない。試行別の入力値・測定不可・備考は紙にしか出ないので、渡せないと情報が失われる。印刷を無効にするのは、**紙が成立しない**とき（判定の取得に失敗した、発行元のテナント名が解決できない）だけにする
- **マスタから消えた項目と、試行・左右の設定変更で表示できない値は警告する**。測定詳細と同じ `measurementDataLoss` を使う。読み取り専用だからと黙って落とすと、記録が無いのと区別が付かない
- 表示できる記録が1件も無いときも**セクションごと消さない**。描画に失敗したのか記録が無いのかを利用者が区別できなくなる

### 値の読み方

- **`value` は入力値そのものではなく代表値**。サーバーが試行のベストを取ってから左右を平均かベストで集約している。測定詳細で入力した値と一致しないことがあるので、「記録値」と呼んで測定値と並べず、代表値であることを表の近くに書く
- **z スコアは常に「高いほど良い」**。棒反応時間・TUG・5m歩行のように低いほど良い項目は、サーバーが符号を反転済みなのでフロントで向きを補正しない
- **`itemEvaluations` に項目名が無い**ので `measurementItemId` で測定項目マスタと結合する。**並び順もマスタ側の順序に従う**（測定のレスポンスと同じく、判定のレスポンスの順序に意味は無い）
- ランクの意味と色の割り当ては `docs/design.md` の「評価の表示」

### アドバイス

アドバイスは判定の他の値と違って**保存される値**で、更新も別エンドポイント（`PUT .../judgment/advice`）になる。

- **判定の表示とは別カードにし、保存ボタンも分ける**。同じフォームに混ぜると、計算結果と入力値の区別が付かなくなる
- 上限は2000文字で、`text.ts` の `isTooLong` / `hasControlCharExceptBreaks` で判定する（改行とタブは許可）。組み立ては `buildAdvicePayload`。**文字数の表示も trim 後で数える**。検証は trim 後なので、生の長さを出すと保存できる入力に上限超過を出してしまう
- **空文字を送ると削除される**。`advice` を送らなければ変更なしという上流の仕様だが、フロントは常に送る（画面で空にした操作を「変更なし」と解釈すると消せなくなる）
- **保存後にレスポンスで入力欄を上書きするときは、返ってこなかった場合に送った値へ戻す**。空文字で埋めると、保存が成功したのに欄が空になり、利用者が失敗と誤解してもう一度保存＝削除してしまう
